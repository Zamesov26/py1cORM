# Участие в разработке

## Локальная проверка

Установите проект вместе с инструментами разработки:

```shell
make install
```

Перед коммитом выполните полный набор проверок:

```shell
make check
```

Для запуска отдельных проверок доступны цели:

```shell
make format
make lint
make typecheck
make test
make coverage
```

`make typecheck` проверяет публичные контракты одновременно через mypy и
Pyright. Примеры ожидаемого вывода типов находятся в `tests/typecheck/`.

## Ветки и pull requests

`main` — единственная долгоживущая ветка и всегда должна оставаться в рабочем,
потенциально релизном состоянии. Постоянная интеграционная ветка `dev` не
используется.

Каждое изменение начинается в короткой ветке от актуальной `main`:

```shell
git switch main
git pull --ff-only
git switch -c feat/order-validation
```

Префикс отражает назначение изменения: `feat/`, `fix/`, `docs/`, `test/`,
`build/`, `ci/`, `refactor/` или `chore/`. Ветка содержит одно связное изменение
и попадает в `main` только через pull request. Прямые push и commit в `main`
запрещены правилами репозитория.

Перед merge pull request должен пройти обязательные проверки CI. После merge
task-ветка удаляется. Стабильные релизные теги создаются только на коммитах
`main`; task-ветки не получают релизных тегов.

## Коммиты

Проект использует Conventional Commits:

```text
<type>(<scope>): <description>
```

`scope` необязателен. Описание пишется на английском языке, в повелительном
наклонении, со строчной буквы и без точки в конце.

| Тип | Назначение | Изменение версии |
| --- | --- | --- |
| `feat` | Новая обратно совместимая функциональность | `MINOR` |
| `fix` | Исправление ошибки | `PATCH` |
| `perf` | Улучшение производительности | `PATCH` |
| `build`, `ci`, `chore`, `docs`, `refactor`, `style`, `test` | Остальные изменения | нет |

Несовместимое изменение отмечается `!` и footer `BREAKING CHANGE:`. Пока версия
ниже `1.0.0`, такое изменение увеличивает `MINOR`.

Релиз запускается вручную workflow `Release` только из ветки `main`. Версию в
`pyproject.toml`, changelog и релизные теги после начальной настройки вручную не
изменяем: это делает `python-semantic-release`.

Перед первым запуском workflow владелец репозитория один раз создаёт исходный
тег на коммите с версией `0.1.0`:

```shell
git tag -a v0.1.0 -m "Release 0.1.0"
git push origin v0.1.0
```

Без исходного тега в расчёт первой автоматической версии попадёт старая история
коммитов, созданная до введения Conventional Commits.
